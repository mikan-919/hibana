# Goal
hibana の型、静的証明、マクロ、効果、能力を設計の核にした hanabi を実装する。サーバーは Linux x86-64 のネイティブ、画面は WASM と JavaScript で動かす。

# Requirements
R1 フレームワーク層にアプリの要素名、投稿の経路、保存ファイル、ポート、入力ファイル、公開関数名を埋め込まない。
R2 JSX の引用符付き属性・式属性・イベント・本文・自己終了タグをマクロで扱い、タグの対応を検査する。
R3 メソッド・パス・経路引数・入力・出力・エラーを一つの api 宣言で共有し、サーバーの登録とクライアントの呼び出しに同じ型を要求する。
R4 record・scalar・union 宣言からデータ型と変換を生成し、アプリでフィールド名を反復しない。
R5 Port・Status・Byte と範囲条件を細分化型で要求し、誤った定数と範囲を型検査で拒否する。
R6 Storage 能力でファイル操作と資産配信を差し替え、ファイル不在と空ファイルを区別する。
R7 クライアントは型付きモデルとメッセージを WASM の参照に保持し、コマンドの応答を型付き関数に戻す。文字列フラグと JavaScript の状態表を使わない。
R8 通信・DOM を効果のハンドラーで差し替えるテストを実装する。
R9 フォームから不正入力をサーバーに送り、4xx の応答を画面に表示する。
R10 ビルドスクリプト・HTTP・ブラウザー操作・再起動後の保存を実行して確認する。
R11 全 hanabi の hb ファイルを整形検査に含め、CSS の参照と実際のクラスを照合する。

# Acceptance
A1 ビルドスクリプトから target/hanabi 一式を生成するテストが通る。
A2 実バイナリへの HTTP 通信で一覧・作成・経路引数付き更新・4xx・不在資産の404・空ファイルの200・切断後の継続・再起動後の保存を確認する。
A3 Playwright がビルド・起動・終了を管理し、デスクトップ幅とスマートフォン幅で入力拒否・作成・編集・一覧の変化・リロード・再起動後の保存を確認する。
A4 cargo test と hibana test が通り、4つの出力先の比較に生成した型・変換・JSX・共有契約を含める。
A5 不正な静的境界、誤った呼び出しやハンドラーの接続、能力と効果の不足、経路の重複、JSX の誤りを拒否する。
A6 検証コマンドと結果を validation.md に残す。未実行の確認を完了と記録しない。

# Constraints
examples は変更しない。追跡済みファイルの移動と削除は Git で行う。確認した作業単位をコミットする。
